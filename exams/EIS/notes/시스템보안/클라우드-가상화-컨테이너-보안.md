> 기준 시점: 2026-11 · 출처: NIST SP 800-125 · SP 800-125A Rev.1 · SP 800-190 · AWS EC2 사용 설명서(IMDS) · AWS Well-Architected · CSA Top Threats 2026

## 한 줄 정의

클라우드 보안은 **가상화 계층의 위협(VM 탈출·컨테이너 탈출)** 과 **책임 공유 모델(이용자가 지킬 몫)** 을 구분하는 것이 출발점이다. 사고의 상당수는 기술 결함이 아니라 **잘못된 설정·취약한 IAM** 에서 나온다.

> [!팁] 최신 출제 범위
> 최신 정보보안기사 범위다. IaaS/PaaS/SaaS 정의는 `robots-모바일앱-클라우드-보안` 노트와 함께 보자.

## 가상화 구조

| 유형 | 설명 | 예 |
|---|---|---|
| **Type 1** (베어메탈·네이티브) | 하드웨어 위에서 **직접** 실행 | ESXi · Hyper-V · Xen · KVM |
| **Type 2** (호스트형) | 호스트 OS **위에서** 실행 | VirtualBox · VMware Workstation |
| **컨테이너** | 호스트 **커널을 공유**, 프로세스 수준 격리 | Docker · containerd |

- NIST SP 800-125: 서버는 주로 베어메탈, 데스크톱은 주로 호스트형으로 가상화
- VM 은 각자 OS 라 **격리가 강하고 무겁다**
- 컨테이너는 가볍지만 커널 공유라 격리가 하이퍼바이저보다 낮다 (SP 800-190 §3.5.2)

## 클라우드·가상화 환경 OS 의 특성

> [!시험] 2027 실기 출제기준 신설 세세항목 1-1-5
> 「운영체제 및 가상화 환경 보안특성 파악하기」 — "클라우드 및 가상화 환경의 운영체제 특성과 보안 특성을 파악할 수 있다." (2027년 시행 출제기준)

| 특성 | 온프레미스 서버 | 클라우드 인스턴스 · 컨테이너 |
|---|---|---|
| 생성 방식 | 설치·수동 구성 | **이미지**(골든 이미지·AMI·컨테이너 이미지)에서 복제 |
| 수명 | 길다 (수년) | **짧다·일시적**(Ephemeral), 오토스케일링으로 생성·삭제 |
| 변경 관리 | 서버에 직접 패치 | **불변 인프라** — 고치지 않고 새 이미지로 교체 |
| 접근 | 콘솔·SSH 비밀번호 | **키 페어**·IAM 역할·세션 관리 서비스 |
| 로그 | 로컬 디스크 | 인스턴스 삭제 시 사라짐 → **중앙 수집 필수** |
| 메타데이터 | 없음 | **IMDS**(`169.254.169.254`)로 자격증명·설정 조회 |

| 보안 특성 | 대응 |
|---|---|
| 이미지 하나가 취약하면 **모든 인스턴스가 취약** | 골든 이미지 하드닝·취약점 스캔·서명 |
| IMDS 를 SSRF 로 호출해 **임시 자격증명 탈취** | **IMDSv2** 강제·홉 제한 (아래 절) |
| 이미지·스냅샷에 남은 키·비밀번호 | 시크릿은 Secrets Manager·볼트로 분리 |
| 인스턴스 삭제 시 포렌식 증거 소실 | 로그·스냅샷 자동 보존 정책 |
| 기본 계정·키 공유 | 인스턴스별 키, OS 계정 대신 IAM 기반 접근 |

### 골든 이미지 · 불변 인프라 근거

- **골든 이미지**: NIST 800-125A HY-SR-9 "Gold standard" — 표준 미준수 이미지는 저장 금지
- 같은 문서 HY-SR-10: 저장된 모든 VM 이미지에 **디지털 서명**
- AWS SEC06-BP02: 하드닝 이미지 = 필요한 것만 남기고 보안 기준으로 구성
- 패치만 하면 기준에서 drift → **새 이미지로 재빌드** 권고
- **불변 인프라**(AWS REL08-BP04): 운영 중 리소스에 패치·설정 변경을 **제자리에서 하지 않음**
- 변경이 없으니 SSH 같은 원격 접속 수단을 꺼 공격면을 줄일 수 있다
- SP 800-190: 컨테이너 안에 **SSH 등 원격 셸 금지**, 호스트 OS 도 불변 운영

### 인스턴스 메타데이터(IMDS) 보호

| 구분 | IMDSv1 | IMDSv2 |
|---|---|---|
| 방식 | 요청/응답 (GET 만) | **세션 지향** — `PUT` 으로 토큰 먼저 발급 |
| 토큰 | 없음 | TTL 1초~6시간, `X-aws-ec2-metadata-token` 헤더 |
| 토큰 필수 시 | — | 토큰 없거나 만료면 `401 Unauthorized` |
| 프록시 방어 | 없음 | `X-Forwarded-For` 포함 `PUT` 거부 |

- 주소: IPv4 `169.254.169.254`, IPv6 `[fd00:ec2::254]`(명시적 활성화 필요)
- 토큰은 **인스턴스 전용 키** — 다른 인스턴스에서 쓰면 거부
- `PUT` 응답 **홉 제한 기본 1** → 외부·중간 장비를 거친 토큰 획득을 막는다
- 단 **컨테이너 환경은 홉 제한 2 권장**(AWS) — 해설: 컨테이너가 한 홉 더 거침
- 계정 기본값을 IMDSv2 로 두거나 계정 수준 **IMDSv2 강제** 가능

> [!함정] IMDS 는 보안 그룹·NACL 로 못 막는다
> AWS 보안 그룹은 메타데이터 트래픽을 필터링하지 않고, NACL 도 IMDS 를 차단할 수 없다. 막으려면 **IMDSv2 필수화** 또는 **메타데이터 엔드포인트 비활성화**.

> [!함정] 클라우드 인스턴스도 OS 패치는 이용자 몫
> IaaS 에서 **게스트 OS 패치·하드닝은 이용자 책임**이다. 하이퍼바이저·물리 서버는 CSP 책임이다.

## 가상화(VM) 위협

| 위협 | 설명 |
|---|---|
| **VM Escape** | 게스트 VM 이 격리를 깨고 하이퍼바이저·다른 VM 메모리 접근 |
| **네트워크 격리 위반** | 악성 VM 의 IP/MAC 스푸핑·가상망 트래픽 스누핑 |
| **자원 고갈(DoS)** | 한 VM 이 호스트 자원 독점 → 다른 VM 서비스 거부 |
| **VM(이미지) Sprawl** | 이미지가 쉽게 늘어나 관리·패치 누락 |
| **이미지·스냅샷 유출** | 비밀번호·개인정보 포함, 스냅샷은 **RAM 내용**까지 |
| **VM Hopping** (업계 용어) | 같은 호스트의 다른 VM 으로 이동 |
| **하이퍼재킹** (업계 용어) | 악성 하이퍼바이저를 하위에 삽입 |
| **부채널** | 공유 캐시·CPU 를 통한 정보 유출 (co-residency) |

- 앞의 세 위협은 SP 800-125A 의 HYP-T1(VM Escape)·T2·T3 와 같다
- VM Escape 원인: 하이퍼바이저 설계 취약점, 악성·취약 디바이스 드라이버
- Sprawl·스냅샷 위험은 SP 800-125 §3.3 근거
- VM Hopping·하이퍼재킹은 NIST 원문에 없는 업계 용어다

대응: 하이퍼바이저 최소화·패치 · 미사용 가상 하드웨어·클립보드/파일 공유 끄기 · 관리 접근 제한 · 관리망 분리(HY-SR-20) · 이미지 서명 · 스냅샷 암호화

## 컨테이너 보안 (NIST SP 800-190)

| 위험 범주 | 대표 항목 |
|---|---|
| 이미지 | 취약점 · 설정 결함 · 내장 악성코드 · **평문 시크릿** · 비신뢰 이미지 |
| 레지스트리 | 비보안 연결 · 오래된 이미지 · 인증·인가 부족 |
| 오케스트레이터 | 무제한 관리 접근 · 컨테이너 간 망 분리 미흡 · 민감도 혼재 |
| 컨테이너 | 런타임 취약점 · 무제한 네트워크 · 비보안 런타임 설정 · 악성 컨테이너 |
| 호스트 OS | 큰 공격면 · **커널 공유** · 부적절 권한 · 파일시스템 변조 |

- 특권 모드(`--privileged`) 컨테이너는 호스트 **모든 장치 접근** → 사실상 호스트 일부

대응 (도구명은 SP 800-190 밖의 업계 예):

| 단계 | 대응 |
|---|---|
| 이미지 | 신뢰 레지스트리 · 스캔(Trivy·Clair) · 서명(Cosign) · distroless |
| 런타임 | 비루트 · `--cap-drop ALL` · **읽기 전용 루트 FS** · cgroups 제한 |
| 런타임 격리 | seccomp 기본 프로필 이상 · SELinux/AppArmor(MAC) |
| 오케스트레이션 | RBAC · NetworkPolicy · Pod Security Standards · 시크릿 암호화 |
| 호스트 | **컨테이너 전용 최소 OS** · 같은 민감도끼리만 한 커널에 |

## 책임 공유 모델

| 계층 | IaaS | PaaS | SaaS |
|---|---|---|---|
| 데이터 · 계정 · 접근관리 | **이용자** | **이용자** | **이용자** |
| 애플리케이션 | 이용자 | 이용자 | CSP |
| OS · 미들웨어 · 런타임 | 이용자 | CSP | CSP |
| 가상화 · 물리 인프라 | CSP | CSP | CSP |

> [!함정] "클라우드는 안전하다"가 아니라 "안전하게 쓸 수 있다"
> 데이터·계정·접근관리는 **어떤 모델이든 이용자 책임**이다. 오픈 버킷, 과도한 IAM 권한 같은 설정 실수가 대표 원인이다.

| 순위 | 위협 | 2024 대비 |

| 4 | 안전하지 않은 인터페이스·API | ↓3위 |
| 5 | 잘못된 설정·부적절한 변경 관리 | ↓1위 |
| 6 | AI 시스템 침해 | 신규 |
| 7 | 지능형 지속 위협(APT) | ↑11위 |
| 8 | 클라우드 보안 전략·거버넌스 부족 | ↓4위 |
| 9 | 안전하지 않은 소프트웨어 개발 | ↓6위 |

## 솔루션 · 인증

| 항목 | 설명 |
|---|---|
| **CASB** | 이용자↔클라우드 사이 프록시 — 가시성 · 접근통제 · DLP · 위협 탐지 |
| **CSPM** | 클라우드 **설정 오류**를 지속 점검 |
| **CWPP** | 클라우드 **워크로드**(VM·컨테이너·서버리스) 보호 |
| **SASE** | SD-WAN + 클라우드 보안(SWG·CASB·ZTNA·FWaaS) 통합 |
| **CSAP** | 공공기관용 클라우드 보안인증(과기정통부 고시), 상·중·하 등급 |
| **ISO 27017 / 27018** | 클라우드 보안통제 / 클라우드 개인정보(PII) 보호 |

> [!현행] CSAP 등급제와 개편 예정
> - **현행(2026-11)**: 「클라우드컴퓨팅서비스 보안인증에 관한 고시」 제2023-4호 — 상·중·하 등급
> - 등급 구분(보도 기준): 상=국가 중대이익·행정 내부업무, 중=비공개 자료, 하=공개 데이터
> - **개편 예정(언론 보도 기준)**: 2026-04 과기정통부·국정원 발표 — 국정원 단일 검증 체계로 통합
> - CSAP 는 ISMS 로 통합, 2027 하반기 시행 예정 — 세부는 아직 확정 고시 아님
> - 2026-09 국정원이 "시행 후 1년 유예"를 검토한다는 보도도 있다
> - 시험 답은 출제 시점 제도 기준 — 현재 문제라면 "CSAP 상·중·하 등급"
