## 한 줄 정의

입력값을 문자열로 이어 붙여 쿼리를 만들면 입력이 **쿼리 구조의 일부**가 되어, **인증 우회 · 데이터 유출 · 명령 실행**이 일어난다. 시험은 *공격 구문 해석 → 유형 구분 → 대응(바인딩)* 순이고, 대응 서술에서 **파라미터 바인딩을 첫 번째로** 써야 한다. {{2-15}} {{4-12}} {{22-10}} {{23-6}} {{30-18}}

## 원리 — 쿼리가 어떻게 바뀌나

```sql
SELECT * FROM member WHERE id='user1' AND pw='입력값'
```

| 입력 | 결과 쿼리 | 효과 |
|---|---|---|
| `pw` 에 `' OR '1'='1` | `... AND pw='' OR '1'='1'` | **항상 참** → 인증 우회·전체 행 노출 |
| `id` 에 `admin'--` | `... WHERE id='admin'--' AND pw=...` | **뒤 조건이 주석 처리** → admin 로그인 |

## 유형

| 유형 | 설명 |
|---|---|
| **Error based** | 오류 메시지에 DB 정보가 노출 |
| **Union based** | `UNION SELECT` 로 다른 테이블 데이터를 결과에 합침 |
| **Blind (Boolean)** | 결과가 안 보여도 참/거짓에 따른 **페이지 변화**로 1비트씩 추출 (`substr()` `length()` `AND 1=1` / `AND 1=2`) |
| **Blind (Time)** | `SLEEP(5)` 등 **응답 시간 차이**로 추출 |
| **Stored Procedure** | `xp_cmdshell` 등으로 OS 명령 실행 |

### 유형 판별 순서 (실무형 대비)

1. 오류 페이지에 SQL 구문·DB 벤더 메시지가 뜨나? → **Error based**
2. `UNION SELECT NULL,NULL...` 로 컬럼 수를 맞추면 데이터가 화면에 찍히나? → **Union based**
3. 화면 변화 없지만 `AND 1=1` / `AND 1=2` 로 페이지가 달라지나? → **Blind (Boolean)**
4. 조건에 따라 응답이 느려지나 (`SLEEP`, `WAITFOR DELAY`)? → **Blind (Time)**

> [!암기] 결과가 보이면 Error/Union, 안 보이면 Blind
> Blind 는 다시 **참/거짓 차이**(Boolean)와 **시간차**(Time)로 나뉜다.

## 대응 — 우선순위 순

1. **PreparedStatement / 파라미터 바인딩** (근본 대응)

   ```java
   PreparedStatement p = con.prepareStatement("SELECT * FROM board WHERE gubun = ?");
   p.setString(1, gubun);          // 입력이 데이터로만 처리 → 쿼리 구조 불변
   ```

   ORM(MyBatis `#{}`, JPA), 동적 SQL 을 쓰지 않는 저장 프로시저도 같은 계열이다.
2. **입력값 검증** — 화이트리스트(타입·길이·형식), 특수문자(`'` `--` `;` `/*`) 필터. **서버 측**에서 (클라이언트 검증은 프록시로 우회됨)
3. **최소 권한 DB 계정** — 애플리케이션 계정에서 DDL·시스템 권한 제거
4. **오류 메시지 최소화** — 상세 DB 오류를 사용자에게 노출 금지
5. **WAF** — 알려진 패턴 차단 (보조)

### 왜 바인딩이 "근본" 인가

바인딩은 쿼리 구조를 먼저 DB 에 넘겨 **컴파일·실행계획을 확정**한 뒤, 입력을 그 자리의 **값(데이터)** 으로만 채운다. 입력이 `' OR '1'='1` 이어도 이미 굳은 구조를 바꾸지 못한다.

반면 필터링은 우회 표현(`OR` 대신 `||`, 인코딩, 주석 삽입 `/**/`)이 계속 나와 **블랙리스트가 완전할 수 없다.** 그래서 필터링은 보조, 바인딩이 근본이다.

### MyBatis 주의

| 표기 | 의미 | 안전성 |
|---|---|---|
| `#{param}` | PreparedStatement 바인딩 | 안전 |
| `${param}` | **문자열 치환** | **SQLi 취약** — ORDER BY 컬럼명 등 불가피할 때만 화이트리스트 검증 후 사용 |

## 함정

> [!함정] 답안에서 감점되는 경우
> - 대응책에 **입력값 필터링만** 쓰면 감점 소지 → **파라미터 바인딩**을 최우선으로 적는다
> - MyBatis `${}` 는 바인딩이 아니다
> - 자바스크립트 검증만으로는 부족하다 — **서버 측 검증**
> - Union 공격은 원 쿼리와 **컬럼 수·데이터 타입**을 맞춰야 결과에 실린다

## 개발보안 빈칸 {{18-3}} {{27-7}}

`( A ) : DB 와 연결된 애플리케이션의 입력값을 조작` → **SQL 인젝션**. 같은 문제의 (B) 는 **XSS**, (C) 는 **운영체제 명령어 삽입**이다. 세 인젝션을 묶어 묻기 때문에 `인젝션-웹셸-요청위조-스머글링` 노트도 함께 본다.

## 기출 포인트

> [!암기] 서술형 3줄 답안
> - SQL 인젝션은 입력이 문자열 연결로 **쿼리 구조의 일부**가 되어 인증 우회·유출·명령 실행을 일으키는 취약점이다.
> - 근본 대응은 **PreparedStatement(파라미터 바인딩)** 로 구조와 데이터를 분리하는 것이며, 입력 화이트리스트·DB 최소 권한·오류 메시지 최소화·WAF 를 함께 쓴다.
> - 결과가 안 보여도 참/거짓 차이(Boolean)·지연(Time)으로 1비트씩 빼내는 **Blind SQL Injection** 이 가능하다.

> [!시험] 이렇게 나온다
> 공격 구문이 만들어 내는 쿼리 해석 · Error/Union/Blind 구분 · 대응책 서술 · MyBatis `#{}` vs `${}`
