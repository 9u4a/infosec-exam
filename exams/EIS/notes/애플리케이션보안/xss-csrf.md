## 한 줄 정의

**XSS** 는 악성 스크립트가 *피해자 브라우저에서 실행*되는 공격이고, **CSRF** 는 로그인된 피해자의 *쿠키가 자동 첨부되는 점*을 악용해 피해자 명의로 요청을 보내는 공격이다. 둘의 **공격 대상이 다르다**는 점이 핵심이다. {{3-9}} {{4-2}} {{15-1}} {{22-15}} {{26-9}} {{31-14}} {{32-6}}

## 1. XSS (Cross-Site Scripting)

응답에 실린 악성 스크립트가 피해자 브라우저에서 실행돼 **쿠키·세션 탈취 · 화면 변조 · 리다이렉트 · 키로깅** 을 일으킨다.

| 유형 | 저장 위치 | 트리거 | 파급력 |
|---|---|---|---|
| **Reflected** (반사형) | 저장 안 됨 | 악성 URL 클릭 (파라미터가 응답에 반사) | 표적(1인) |
| **Stored** (저장형) | 서버 DB (게시글·댓글·프로필) | 페이지 열람 | **최대** (열람자 전원) |
| **DOM Based** | — (서버 안 거침) | JS 가 `location` `innerHTML` 등을 안전하지 않게 처리 | 클라이언트에서 발생 |

점검: `<script>alert(document.cookie)</script>` 를 넣어 실행되면 필터링이 없는 것이다.

### 대응

- **출력 시 컨텍스트별 인코딩** — HTML body / 속성 / JS / URL / CSS 가 각각 다르다 (**가장 중요**)
- 입력값 검증 (태그 허용 시 화이트리스트)
- **CSP** 헤더로 인라인 스크립트·외부 출처 제한
- 쿠키 **HttpOnly** (JS 접근 차단 → 쿠키 탈취 방어)
- 프레임워크 자동 이스케이프 (React JSX · Thymeleaf)

### DOM Based XSS 판별

서버 응답은 깨끗한데, 클라이언트 JS 가 `location.hash` · `document.URL` · `referrer` 같은 **소스**를 `innerHTML` · `document.write` · `eval` 같은 **싱크**에 안전 처리 없이 넣을 때 생긴다.

- 서버 로그·프록시로 안 잡히고 **브라우저에서 페이로드가 실행**된다
- `#` 뒤 값은 서버로 가지 않아 **WAF 도 못 막는다**
- 대응: `textContent` 등 안전한 DOM API, 프레임워크 바인딩

## 2. CSRF (Cross-Site Request Forgery)

인증된 피해자의 브라우저가 **쿠키를 자동 첨부**하는 점을 악용해, 공격자 페이지에서 **피해자 명의의 상태 변경 요청**(비밀번호 변경·이체·설정 변경)을 유발한다. 서버가 "정상 폼 요청"과 "위조 요청"을 구분하지 못하는 것이 원인이다.

### 대응

| 방법 | 설명 |
|---|---|
| **CSRF 토큰** | 요청마다 임의 토큰을 발급해 세션 저장값과 대조 (외부 페이지는 토큰을 알 수 없음) |
| **SameSite 쿠키** | `Lax` / `Strict` — 교차 사이트 요청에 쿠키 미전송 |
| **Referer / Origin 검증** | 요청 출처 확인 |
| **재인증** | 중요 기능에서 비밀번호 재입력 |
| 메서드 | 상태 변경은 GET 금지, **POST + 토큰** |

## 3. XSS vs CSRF — 헷갈림 축

| | XSS | CSRF |
|---|---|---|
| 공격 대상 | **사용자(브라우저)** — 스크립트 실행 | **서버** — 위조 요청 처리 |
| 필요 조건 | 취약 페이지에서 스크립트가 **실행**됨 | 피해자가 **로그인 상태**(유효 쿠키 보유) |
| 스크립트 실행 | 필요 (핵심) | **불필요** (이미지 태그·자동 폼 제출로 충분) |
| 근본 원인 | 출력 시 미인코딩 | 요청의 **출처를 검증하지 않음** |
| 대표 방어 | 출력 인코딩 · CSP · HttpOnly | CSRF 토큰 · SameSite · Referer 검증 |

> [!함정] 판별 팁
> "쿠키를 특정 사이트로 몰래 **전송**" = XSS (스크립트가 `document.cookie` 를 빼냄)
> "피해자 **명의로 요청**이 나감" = CSRF
> XSS 가 있으면 CSRF 토큰까지 읽어 낼 수 있어 **CSRF 방어가 무력화**된다.

## 4. 쿠키 · 세션

### 쿠키 보안 속성 {{22-15}}

| 속성 | 기능 | 방어 대상 |
|---|---|---|
| **Secure** | HTTPS 연결에서만 전송 | 평문 구간 스니핑 |
| **HttpOnly** | JS(`document.cookie`) 접근 차단 | XSS 쿠키 탈취 |
| **SameSite** | 교차 사이트 요청에 미전송 | CSRF |
| **Expires / Max-Age** | 만료 시각 | 탈취 쿠키 재사용 창 축소 |

### 쿠키 vs 세션 {{31-18}}

| | 쿠키 | 세션 |
|---|---|---|
| 저장 위치 | **클라이언트** (브라우저) | **서버** (클라이언트엔 세션 ID 만) |
| 전달 | `Cookie` / `Set-Cookie` 헤더 | 쿠키에 담긴 세션 ID 로 서버가 조회 |
| 보안 | 스니핑·XSS·변조로 노출·조작 | 값이 서버에 있어 상대적으로 안전, **세션 ID 탈취(하이재킹)** 는 여전히 위험 |
| 수명 | `Expires` / `Max-Age` | 서버 타임아웃 |

세션 대응: 로그인 후 **세션 ID 재발급** · 유휴 타임아웃 · `Secure` + `HttpOnly` + `SameSite` · 전 구간 HTTPS

## 5. URL Rewrite / mod_rewrite {{31-10}}

**IIS 의 URL Rewrite 모듈**(Apache 는 `mod_rewrite`)은 요청 URL 패턴을 정의해 다른 URL 로 **재작성·리디렉션**한다.

- 보안 활용: 악성 패턴 URL 차단 · 확장자 숨김 · HTTPS 강제 · 트래버설·인젝션 URL 정규화·거부
- 그 자체가 방화벽은 아니며 WAF·입력 검증을 보완하는 수단이다

## 기출 포인트

> [!암기] 서술형 3줄 답안
> - **XSS**: 입력한 스크립트가 응답에 실려 **피해자 브라우저에서 실행**되어 쿠키·세션 탈취·화면 변조. **출력 시 컨텍스트별 인코딩**이 핵심, CSP·HttpOnly·입력 검증 병행.
> - **CSRF**: 로그인된 브라우저가 쿠키를 자동 첨부하는 점을 악용해 **피해자 명의 요청**을 유발. **CSRF 토큰 · SameSite · Referer 검증**.
> - 저장형 XSS 는 열람자 전원에게 퍼져 파급력이 가장 크고, XSS 가 있으면 CSRF 토큰도 탈취되어 방어가 무력화된다.
