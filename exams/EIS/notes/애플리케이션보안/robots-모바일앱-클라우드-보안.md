## robots.txt (13-16, 15-2, 24-6)

- **로봇 배제 표준(Robots Exclusion Protocol)** 을 따르는 일반 텍스트 파일. 웹사이트 **루트 디렉터리**(`/robots.txt`)에 위치.
- 검색 로봇(크롤러)의 접근 허용/제한을 **권고**할 뿐 강제력 없음.
- 문법:
  ```
  User-agent: googlebot
  Allow: /
  User-agent: googlebot-image
  Disallow: /private/
  ```
- **보안 주의**: 관리자 페이지·백업 경로를 `Disallow` 에 적으면 오히려 **위치를 알려주는 꼴** → 민감 경로는 인증으로 보호하고 robots에 노출하지 않는다.

## FTP 능동/수동 모드 (9-14, 10-2)

| 채널 | 포트(서버) | 역할 |
|---|---|---|
| 제어 채널 | **21** | 클라이언트가 접속·명령 전달, 세션 내내 유지 |
| 데이터 채널 | **20**(Active) | 파일·디렉터리 목록 전송 |

- **Active 모드**: 서버가 **20번 → 클라이언트의 임의 포트(1024↑)** 로 역방향 연결.
  클라이언트 방화벽/NAT가 이 인바운드를 막으면 **목록·전송 실패**.
- **Passive 모드**: 서버가 데이터용 임의 포트를 열고 대기, **클라이언트가 접속**. → 클라이언트 방화벽 문제 해결(클라이언트에서 `passive`/`pasv` 설정).
- 보안: 평문 전송 → **FTPS**(FTP+TLS) 또는 **SFTP**(SSH) 사용, `chroot` 로 상위 디렉터리 접근 차단.

### FTP·파일전송 관련 공격 (2-3)

| 공격 | 설명 |
|---|---|
| **TFTP 공격** | **UDP 69** 포트, **인증 없이** 파일 전송하는 TFTP 서버를 악용해 설정파일·부팅이미지 유출·변조 |
| **Anonymous FTP 공격** | 익명(anonymous) 접속을 허용한 FTP 서버에 접근해 파일 열람·업로드(웹셸)·디렉터리 정보 수집 |
| **FTP Bounce Attack** | `PORT` 명령의 목적지를 검사하지 않는 FTP 설계 결함을 악용 → FTP 서버가 **제3의 시스템**으로 데이터를 보내게 해 포트스캔·우회 공격 (방화벽 뒤 스캔) |

- 대응: 익명 FTP 비활성/최소화, TFTP 미사용(필요 시 ACL·읽기전용), `PORT` 명령 목적지 검증, Passive 모드, FTPS/SFTP 전환.

## 클라우드 서비스 유형 (12-6)

| 유형 | 제공 범위 | 사용자 책임 | 예 |
|---|---|---|---|
| **IaaS** | 서버·스토리지·네트워크 (인프라) | OS·미들웨어·앱·데이터 | AWS EC2, GCP CE |

## 클라우드 배포 모델 4가지 (최근 출제 증가)

| 모델 | 설명 | 특징 |
|---|---|---|
| Public Cloud | 불특정 다수에게 인터넷으로 제공 | 비용 저렴, 보안 위험 상대적으로 높음 |
| Private Cloud | 단일 조직 전용 구축·운영 | 높은 보안·높은 비용 |
| Hybrid Cloud | Public+Private 혼합 운영 | 유연성 높음, 관리 복잡 |
| Community Cloud | 동일 목적·규제를 가진 조직 간 공유 | 금융권·공공기관 등 |

## 클라우드 보안 핵심 기술 3종 (CASB / SWG / ZTNA)

| 기술 | 역할 | 위치 |
|---|---|---|
| **CASB**(Cloud Access Security Broker) | 사용자↔클라우드(SaaS) 사이에서 **가시성·컴플라이언스·데이터 보안(DLP 연동)·위협 방어** 4기능 제공 | 클라우드 접근 중간 프록시 |
| **SWG**(Secure Web Gateway) | 인터넷 트래픽 필터링·모니터링으로 악성 사이트 접근 차단 | 웹 접근 보안 게이트웨이 |
| **ZTNA**(Zero Trust Network Access) | "아무도 신뢰하지 않는다" — 내부 사용자도 매 접근마다 인증·인가 | 네트워크 접근 제어 |

**SecaaS**(Security as a Service): 보안 솔루션 자체를 클라우드로 제공(인증·안티바이러스·IDS·DLP·IAM 등). 장점 — 초기 투자비용 절감, 탄력적 확장(Scalability). 단점 — 인터넷 의존성, 데이터 주권 문제.

## 모바일 관리 체계 (MDM / MAM / MCM / EMM) — BYOD 대응

| 기술 | 역할 |
|---|---|
| **MDM**(Device) | 기기 전체 제어 — 원격 잠금·삭제, 정책 배포 |
| **MAM**(Application) | 업무 앱만 분리 관리(개인 앱과 컨테이너 분리) |
| **MCM**(Content) | 업무 문서·콘텐츠 단위 암호화·접근 통제 |
| **EMM**(Enterprise Mobility Management) | MDM+MAM+MCM 통합 솔루션 |

## 가상화 보안 (클라우드 기반 인프라)

| 구성요소 | 위협 | 대응 |
|---|---|---|
| 하이퍼바이저 | **VM Escape**(가상머신 탈출) | 패치 관리, 하이퍼바이저 접근 통제 |
| VM 간 통신 | VM-to-VM 스니핑 | 가상 네트워크 세분화(VLAN) |
| 스냅샷 | 민감 데이터 포함 유출 | 스냅샷 암호화·접근 제한 |
| 컨테이너 | 컨테이너 이탈, 이미지 취약점 | 이미지 서명 검증, 네임스페이스 격리 |

**IAM vs EAM**: EAM(Enterprise Access Management)은 OS·DB·서버 등 사내 자원 접근 통합 관리, IAM(Identity & Access Management)은 신원 확인(Identity)+접근 제어(Access, RBAC/ABAC)+생명주기(계정 생성~삭제) 관리까지 포괄하는 확장 개념.

## 서브도메인 테이크오버 (20-9)

클라우드/외부 서비스용으로 서브도메인에 **CNAME** 을 걸어 두고 서비스는 해지했지만 **DNS 레코드를 안 지운** 경우 →
공격자가 그 서비스에 같은 이름으로 리소스를 생성해 서브도메인을 **탈취** → 피싱·쿠키 탈취.
- 대응: 서비스 해지 시 DNS 레코드 즉시 삭제, 소유하지 않은 리소스를 가리키는 dangling 레코드 정기 점검.

## 모바일 딥링크 (18-10, 28-12)

앱 내 **특정 화면으로 바로 이동**시키는 URL 스킴(`myapp://pay?...`) / 유니버설·앱 링크.
- 악용: 조작된 딥링크로 접속 유도 → 인증·검증 없이 민감 화면(카드정보·주소) 노출, 파라미터 조작으로 **의도치 않은 계좌이체**.
- 대응: 딥링크 파라미터 **서버 측 재검증**, 민감 액션은 재인증, 화이트리스트 호스트, `autoVerify` 앱 링크 사용.

## 인증서 고정 (Certificate Pinning) — 29-13

1) **정의/목적**: 앱에 서버 인증서(또는 공개키) 지문을 **미리 저장**, TLS 연결 시 실제 인증서와 일치할 때만 통신 허용 → **중간자(MITM)** 공격(사설 CA·프록시) 방지.
2) **핵심 요소**: ① 고정 대상(리프 인증서 / 중간 CA / **공개키 SPKI 해시**) ② 백업 핀(교체 대비) ③ 핀 만료·갱신 정책.
3) **우회 방법**: ① 루팅/탈옥 후 **Frida·Objection** 으로 검증 함수 후킹 ② 앱 리패키징(스마리 패치) ③ 사용자 CA 신뢰 + `network_security_config` 조작.
