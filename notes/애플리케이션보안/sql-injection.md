## 원리

입력값을 문자열로 이어붙여 쿼리를 생성하면 입력이 **쿼리 구조의 일부**가 된다.

```sql
SELECT * FROM member WHERE id='user1' AND pw='입력값'
```
`pw` 자리에 `' OR '1'='1` → `... AND pw='' OR '1'='1'` → **항상 참** → 인증 우회 / 전체 행 노출
`id` 자리에 `admin'--` → `... WHERE id='admin'--' AND pw=...` → **뒤 조건 주석 처리** → admin 로그인

## 유형

| 유형 | 설명 |
|---|---|
| **Error based** | 오류 메시지에 DB 정보가 노출 |
| **Union based** | `UNION SELECT`로 다른 테이블 데이터를 결과에 합침 |
| **Blind (Boolean)** | 결과가 안 보여도 참/거짓에 따른 페이지 변화로 1비트씩 추출 (`substr()`, `length()`, `AND 1=1`/`AND 1=2`) |
| **Blind (Time)** | `SLEEP(5)` 등 응답 시간 차이로 추출 |
| **Stored Procedure** | `xp_cmdshell` 등으로 OS 명령 실행 |

### 유형 판별 순서 (실무형 대비)
1. 오류 페이지에 SQL 구문·DB 벤더 메시지가 뜨나? → **Error based**
2. `UNION SELECT NULL,NULL...` 로 컬럼 수를 맞추면 데이터가 화면에 찍히나? → **Union based**
3. 화면엔 변화 없지만 `AND 1=1` / `AND 1=2` 로 페이지가 달라지나? → **Blind (Boolean)**
4. 조건에 따라 응답이 느려지나(`SLEEP`, `WAITFOR DELAY`)? → **Blind (Time)**
- 즉 **결과가 보이면** Error/Union, **안 보이면** Blind. Blind는 다시 참/거짓 vs 시간차로 나뉜다.

## 대응 (우선순위)

1. **PreparedStatement / 파라미터 바인딩** (근본 대응)
   ```java
   PreparedStatement p = con.prepareStatement("SELECT * FROM board WHERE gubun = ?");
   p.setString(1, gubun);          // 입력이 데이터로만 처리 → 쿼리 구조 불변
   ```
   - ORM(MyBatis `#{}`, JPA), 저장 프로시저(동적 SQL 미사용)
2. **입력값 검증** — 화이트리스트(타입·길이·형식), 특수문자(`'`, `--`, `;`, `/*`) 필터 (서버 측 — 클라이언트 검증은 프록시로 우회됨)
3. **최소권한 DB 계정** — 애플리케이션 계정에 DDL·시스템 권한 제거
4. **오류 메시지 최소화** — 상세 DB 오류를 사용자에게 노출 금지
5. **WAF** — 알려진 패턴 차단 (보조)

## MyBatis 주의

- `#{param}` → PreparedStatement 바인딩 (안전)
- `${param}` → 문자열 치환 (**SQLi 취약**) — ORDER BY 컬럼명 등 불가피할 때만 화이트리스트 검증 후 사용

## 왜 파라미터 바인딩이 "근본" 대응인가

바인딩은 쿼리 문장(구조)을 먼저 DB에 넘겨 **컴파일·실행계획을 확정**한 뒤, 사용자 입력은 그 자리의 **값(데이터)** 으로만 채운다. 입력이 아무리 `' OR '1'='1` 여도 이미 굳은 쿼리 구조를 바꿀 수 없다. 반면 입력값 필터링은 우회 표현(`OR` 대신 `||`, 인코딩, 주석 삽입 `/**/`)이 계속 나와 **블랙리스트가 완전할 수 없다** — 그래서 필터링은 보조, 바인딩이 근본.

## 서술형 3줄 요약 답안

- SQL 인젝션은 사용자 입력이 문자열 연결로 **쿼리 구조의 일부가 되어** 인증 우회·데이터 유출·명령 실행을 일으키는 취약점이다.
- 근본 대응은 **PreparedStatement(파라미터 바인딩)** 로 쿼리 구조와 데이터를 분리하는 것이며, 입력값 화이트리스트 검증·DB 계정 최소권한·오류메시지 최소화·WAF를 함께 적용한다.
- 결과가 보이지 않아도 참/거짓 응답 차이(Boolean)나 지연(Time)으로 데이터를 1비트씩 빼내는 **Blind SQL Injection** 이 가능하다.

## 함정

- "대응책?" 에 **입력값 필터링**만 쓰면 감점 소지 — **파라미터 바인딩**을 최우선으로 적어야 한다.
- MyBatis `${}` 는 바인딩이 아니라 **문자열 치환**이라 취약. `#{}` 가 안전.
- 클라이언트(자바스크립트) 검증은 프록시로 우회되므로 **서버 측 검증**이어야 한다.
- Union 공격 전제: 원 쿼리와 **컬럼 수·데이터 타입**을 맞춰야 결과에 실린다.

## SW 개발보안 빈칸 (18-3, 27-7)

`( A ) : DB와 연결된 애플리케이션의 입력값을 조작` → **SQL 인젝션**.
같은 문제의 (B)는 **XSS**, (C)는 **운영체제 명령어 삽입**이 정답 — 세 인젝션을 묶어 물으므로
`인젝션-웹셸-요청위조-스머글링` 노트도 함께 참고.
